## 3. Re-aim: unique vs shared per-element work (coordinator note, 17:40)

B0's first timed run showed the v2 baseline (V glyph rule already 226 B) at the same 40.2 s/token as the pinned v1
bundle (4,006 B rule) — declared bytes on IDENTICAL-declaration leaves do not move the token because Blink's
MatchedPropertiesCache shares the applied result. `F2/unique_work.py` classifies every element in the core-block
subtree (`F2/unique_work_{baseline,F2}.md`): shared rule bytes/var()/calc() per element, unique bytes (inline style,
`#id` / `:nth-child` rules), number of distinct (rule-set, parent-class) signatures = MPC groups, and a modelled
µs/pass = 4.45 µs·n + 36.5 ns·unique bytes + 36.5 ns·shared bytes·groups + 10 µs·@function calls·groups.

Reading:
* **Per-element unique var()/calc() in the two target populations was already 0** in baseline: every pack leaf and
  every V glyph has no inline style and no element-specific rule; they differ only by which of 4 (packs) or 96
  (glyphs) shared rule sets they match, and their parents' inherited data are identical within a group → 4 and 96
  MPC groups. The 122 MB / 1.4 MB byte figures are therefore applied ~4 and ~96 times per pass, not 3,072 and
  6,144 times. What each leaf still costs is the per-element floor (4.45 µs) + MPC lookup + a text run whose font
  instance must be resolved: F2 removes 3,072 of those elements outright (proj) and cannot remove the 6,144 glyphs
  without the `fallback` value layout (out of scope: E4 #298 risk, un-validated in Chrome 153).
* The 12,274-element pass (7.8/token, 530 ms = 43 µs/element measured) is the whole core with the V-glyph gate closed;
  the model puts it at ≈220 ms of style work (baseline) → ≈195 ms (F2): −3,072 elements (−14 ms), −4 pack-rule
  applications (+1 bigger `.shared-proj` list: −8 ms net), −3,072 `@function` calls (−9 ms per fc-consumer restyle).
  The remaining ≈300 ms gap between model and measurement is not declaration work (candidates: font-instance
  resolution for 7,687 carriers whose inherited `font-variation-settings` changed, animation/timeline bookkeeping on
  the consumers, `:has()`/container-query invalidation) — that is F3/F5 territory.
* The ~3k-element passes (2,935 ≈ core minus the qkv gate; 3,089 / 3,545 / 3,856 = the same set ± one stage) contain
  NO leaf population; their unique work sits on ≈15 singleton elements (consumers, LN, reset, lists: ≈1.5 MB of var()
  declarations ≈ 55 ms) plus 2,304–3,072 carriers with unique inline timelines (floor ≈ 15 ms). Fix 2 changes those
  passes only through (c) when fc consumers are dirtied.
* Honest expectation for B0's bench: **≤ 0.3–0.5 s/token** from this bundle (≈ −30 ms on each of the ~8 whole-core
  passes + the GELU saving), i.e. it will NOT meet the Fix-2 pass criterion (−6 s) on its own; the byte/element
  slimming mainly buys RSS/parse and removes one population from the DOM for later fixes.
