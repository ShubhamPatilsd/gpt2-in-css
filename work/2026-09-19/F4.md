|---|---|---:|---:|---|---|

### 2.2 Packed layout

- **KV banks (flag `F4_PACKED_BANKS`, default ON):** per slot S: `--fc-k-S` and `--fc-v-S` (`syntax:"*"`, 768 axes each) + 24 scales
  `--fc-ks-S-H`, `--fc-vs-S-H` unchanged = **26 latches per slot (was 48)**; base list 8 × 26 = **208 names (was 384)**.
  Head h's K coordinates use tags `K{h·64+i:03X}` (K000…K2FF), V coordinates `V{h·64+i:03X}`; Q000…Q063 and P000 stay shared
  (each glyph appends its own head's query / weight). The live lists `--fvs-live-k/v-H` on `.fvs-query` are emitted with the head tags,
  the write rule becomes `--fc-k-S:var(--fvs-live-k-0),…,var(--fvs-live-k-11)` (same bytes as the 12 separate declarations), the alias rule
  `--fr-k-S:var(--fc-k-S)` (F5's filled-slots filter kept; slot index parsed positionally), the score glyph reads
  `var(--fr-k-S),var(--fvs-query-H)` in `font:512px FvsDot{H}`, the V glyph reads `var(--fr-v-S),"P000" var(--fw-H-S)` in `FvsValue{H}`.
  Fonts: 12 dot + 12 value fonts retagged from `font-vector-operators-v2/{dot,value}.woff2` into `F4/assets/font-vector-operators-f4/`
  (only `fvar` tags, STAT and `name` change; HVAR/hmtx/cmap/glyf/loca/maxp/hhea byte-identical, asserted at generation — F2's recipe).
  256-axis ceiling (S2 #12): each font keeps 128 / 65 axes; only the LIST carries 768 (+64 / +1) tags. F2 relies on the same "font ignores
  tags it does not define" behaviour with 3,072-tag lists over 12 × 256-axis fonts and passed 8/8 in Chrome 153 (F2 §6); the two-block
  global4 bundle validated it earlier. The one Chrome run in §5 is the validation for these fonts.
- **Head input (flag `F4_PACKED_HEAD`, default ON):** `.head-input-bank{--hq-i:round(nearest,calc(var(--final-h-i)/266.248396912*16384),1)}`
  (768 registered `<number>`, `inherits:false`, same double ops in the same order as the head.css expression on `--h_i = --final-h-i`),
  `--head-fvs:"X000" var(--hq-0),…` (`*`, `inherits:true`, 1 latch), `transition-property:--head-fvs,--head-input-epoch` +

### 2.3 Expected effect (F5 §4: ≈5.7 µs per in-delay transition on EVERY style pass; 171 passes/token)

| population | running latches before -> after | Δ per pass (ms) | Δ per token (s) |
|---|---:|---:|---:|
| KV banks at p=8 | 4,608 -> 2,496 | −12.0 | **−2.06** |
| KV banks per position | +576 -> +312 per position | −1.5 / position | slope **−0.26 s/token per position** (F5's 0.56 -> 0.30) |
| head input | 769 -> 2 | −4.4 | **−0.75** (flat) |
| loop banks | 769–1,538 (unchanged) | 0 | 0 |
| total at p=8 | 5,377+loop -> 2,498+loop | −16.4 | **≈ −2.8 s/token at p=8, ≈ −1.0 at p=1** |

The orchestrator's 4-per-slot target (48 -> 4, ≈ −25 ms/pass) is not reachable without a numerics change: the 24 per-slot scales are
numbers. Documented follow-ups (2.4). Listed-name compares scale down with the same ratio (384 -> 208 per bank), so the estimate holds
whichever of the two mechanisms F5's 5.7 µs figure blends.

### 2.4 Rejected ways to pack the scales (for the record)
1. Scale as an extra font axis (trilinear region Q·K·S): the axis coordinate is F2Dot14 in the font, so an unbounded scale must be normalised
   by a fixed KMAX and loses ~KMAX/16384 absolute precision (0.06 for KMAX=1000 at ks≈5 = 1 %); an exact hi/lo two-axis split needs new HVAR
   regions with deltas divisible by the split ratio — a new operator font and a numerics re-validation, not this round.
2. Per-slot instead of per-head scale (max over 12 heads): heads with small K/V magnitude lose up to ~20× axis resolution — rejected.
3. Packing ks and vs into one double (`ks·2^24 + vs`) and extracting with `round()`: only 24 -> 12 and not exact — rejected.
4. Reading a scale back from a glyph advance via `tan(atan2(100cqw,1px))`: needs a container per (head, slot) inside the score track, and the
   advance is again 2.14-quantised — rejected.

Reading:
1. **The transition COUNT is not the cost.** 4,608 vs 2,496 running transitions with the same bytes: 36.2 vs 35.7 ms. Halving the count
   (run 1) saved 3.3 ms of 35 in the banks and 0.3 ms of ~1.8 for the head+loop numbers (≈0.4 µs per `<number>` transition). F5's 5.7 µs
   figure was an average over 9,216 1 KB lists + 9,216 numbers; the per-transition term is small.
2. **The cost is the BYTES of the retained `*` lists**: ≈8 ns per byte (49.6 → 24.4 ms for 4.65 → 1.54 MB) plus ≈0.15 µs per axis entry,
   paid on every pass in which the 12 banks are restyled (they are restyled on every unrelated mutation because their transitions are
   in effect — backwards fill during the delay). The demo at p=8 holds 12 × 8 × 24 × 64 = 147k axis entries; in the calc form that is
   ≈6.6 MB → the measured 32–50 ms per pass; in the numeric form ≈2.2 MB → ≈24–36 ms. RSS follows bytes too (202 → 175 MB).
3. Consequence for the design in §2: packing (48 → 26 per slot) is kept (−3 ms/pass, −9 % of bank RSS, fewer alias/list objects) but the
   lever that matters is entry bytes, hence `F4_NUMERIC_LISTS`. A further ~30 % would come from shorter numbers (4–5 significant digits
   instead of Blink's 6 — a precision trade the numerics owner must approve) — see §6.

Revised expectation (replaces §2.3; per pass in which the banks are restyled, × up to 171 passes/token):
KV banks at p=8: calc/48-per-slot ≈ 35 ms → numeric/26-per-slot ≈ 22–24 ms (−11 to −13 ms, i.e. −1.9 to −2.2 s/token if every pass
restyles the banks, proportionally less if only frames do); slope ≈ −0.25 s/token per position; head 769 → 2 ≈ −0.3 ms/pass (−0.05 s/token);
loop banks unchanged. `combined-calc` (packing only) ≈ −3.6 ms/pass ≈ −0.6 s/token at p=8. B0's numbers decide.

## 6. Residual risks / follow-ups

- `F4_NUMERIC_LISTS` changes the rounding point of the latched K/V entries (round6(q/s) instead of round6(q)/round6(s) evaluated later):
  same 1e-6 class as before (F2 §6), 8/8 ids and equal max cache rmse in Chrome, but not bit-identical to `combined-calc`. `F4_NUMERIC_LISTS=0`
  reverts (that build is `combined-calc`).
- Per-glyph `font-variation-settings` lists are now 768 (+64 / +1) tags: F2's mechanism, validated here for 24 fonts × 96 glyph classes ×
  8 tokens; each V glyph substitution is ~12× longer, so if B0 sees the ~7k-element (score-gate-open) pass grow, the MPC is not sharing the
  6,144 glyph leaves as assumed (then the fallback is `F4_PACKED_BANKS=0` with numeric entries — a build not made this round).
- The micro-test says the bank cost is bytes per restyled pass (~8 ns/B) and the banks are restyled on every pass while their transitions
  are in effect; the remaining ≈2.2 MB at p=8 costs ≈22–36 ms/pass. Next levers, in order: (1) 4–5 significant digits per entry (needs a
  numerics decision; ~−30 %), (2) F3 — fewer passes/frames per token multiplies everything here, (3) not restyling inactive banks — impossible
  while `*` state travels by inheritance (F5 §2), unless per-layer banks become siblings that the selected layer *copies from* once per
  layer (a copy is a `var()` of an inherited value — still inheritance; no CSS-only path found).
- The head-input change relies on `transition-behavior:allow-discrete` for a `*` transition (the KV banks already do) and on exact integer
  serialisation of typed numbers into a `*` list (confirmed by the read-back sample).
- Loop banks (769–1,538 `<number>` transitions ≈ 0.3–0.6 ms/pass) left as is: numbers → widths cannot be packed.
- Disk: work/ bundles are 46–49 MB each (fonts symlinked/relative), F4 dir 13 MB; 9.3 GB free at the end.
