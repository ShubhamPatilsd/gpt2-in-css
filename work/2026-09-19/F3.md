Findings (each from the table; Chrome 153):
1. **The mechanism works and is frameless**: one `UpdateLayoutTree`, one `Layout`, one `Commit`, zero
   `BeginMainThreadFrame`-driven re-entries; the 128 interleaved container recalcs happen inside the single
   Layout (Performance.getMetrics counts them as `RecalcStyleCount` +129, the trace shows one ULT with
   `elementCount` 261 ≈ 2 per container + anchors). Cost ≈ **40–55 µs per container level** (4.8 ms /128,
   13.6 ms /250, 28 ms /500), i.e. two values per ~50 µs.
2. **Chromium rule that made E5 #301 "resolve to zero" is the acceptable-anchor containing-block rule, not size
   containment**: an anchored element may only see anchors that are descendants of its containing block (or
   anything, if its containing block is the initial containing block). Nested `position:absolute` containers
   make each container the CB of the next, hiding the outer anchors (`abs` → 0). `position:fixed` containers all
   have the viewport as CB, so every anchor in the document is acceptable (`fixed`, `late`, `inside` all exact).
   `container-type:size` does not hide anchors (`inside` exact). Tree order does not matter for **in-flow** anchors
   (`late` exact) — but it does for anchors hosted inside other positioned subtrees, see §3b.
3. `anchor-size()` on a non-positioned element is still not accepted in Chrome 153 (`static` → `width:auto`).
4. **Depth cap is the HTML parser's 512-element nesting limit** (elements beyond are re-parented): one chain can
   hold ≈ 250 containers = **≈ 500 values**; at D = 500 exactly the first 508 values (254 containers + 4 wrapper
   levels) survive. Declarative shadow roots do reset the parser depth but **anchor names are tree-scoped**, so a
   shadow-tree chain cannot see light-DOM anchors (`shadow` → 0 after the first segment). Layout itself has no
   problem with 500 containers (28 ms).
5. Precision: exact for widths ≤ 32,768 px (the glyph-advance cap the fonts already respect); at 2^25 px the
   cq-unit path loses ~6 bits, so packing must stay below ~2^24 px per dimension.

## 4. What integration into the emitter actually requires (sizing, from the prototypes)

The chain is a **gather into one subtree**; its hard limits are (a) ≤ ≈ 500 values per chain (parser nesting
cap, §2 finding 4), (b) inheritance only flows down from the chain bottom, (c) anchors must not depend on the
anchored element (cycle → fallback). Mapping the reused-graph layer onto it:

| Boundary today (values) | Frameless replacement | New elements |
|---|---|---|
| QKV 2,304 → one `.fvs-query` | 12 **per-head columns**: 96-container chain gathering q_h,k_h,v_h (192) → that head's bank / score glyphs / 4-container score chain / softmax / V rows (64 × slots) | 12 × (96 + 4) containers |
| ctx 768 → attn-proj (3 input shards) | 3 shard columns: 128-container chain gathering 4 heads' ctx → 768 single-glyph rows (`anchor-name`) | 3 × 128 containers, 2,304 glyph anchors |
| attn 768 → `--r` (+x) → LN2 → fc | `r` needs all 768 on one element: 2 chains ≤ 500 **+ cross-chain partial sums for LN2 via 2 extra anchor levels**; fc rows then sit under… **3 shard columns** (n2 must be split 256-wise for the 3 fc shard fonts) → 3,072 × 3 glyph anchors | 3 × 128 (+2) containers, 9,216 anchors |
| fc 3,072 → proj (12 shards) | 12 shard columns: 128-container chain with `calc(anchor-size(a)+anchor-size(b)+anchor-size(c))` widths (sums the 3 fc shard glyphs) + GELU decode → 768 single-glyph proj rows | 12 × 128 containers, 9,216 anchors |
| proj 768 → `--out` (+r) → next layer | 3 chains × 128 containers, widths = Σ of 12 shard anchors, `r` re-transported as 768 anchors (offset for sign) | 3 × 128 containers, 768 anchors |
| **per layer** | | **≈ 4,400 containers, ≈ 27k anchors** (vs 8,548 carriers + 22 readers today) |

Two ways to close the layer loop:
* **A. keep the reused graph**: only the layer→layer feedback stays a timeline/latch hop (loop bank) plus the
  SMIL handshake → **≈ 1 frame + 4–5 recalcs per layer ≈ 15 frames/token (5.7× fewer)**; predicted per-token
  transport cost ≈ 12 × 0.16 s (§2b) + 12 frames ≈ 2–4 s instead of ≈ 15–20 s. DOM grows by ≈ 30k positioned
  elements (+ ≈ 1 GB RSS at the §2b rate unless painting is suppressed).
* **B. unroll 12 layers as sibling column groups** (layer L+1's x-chain reads layer L's `out` anchors directly):
  **1 frame per token**, no SMIL handshake at all (Fix 6 becomes moot), but 12× the layer DOM (≈ 840k elements,
  ≈ 12–20 GB RSS at the measured rate) — not viable on this 16 GB host without first fixing the per-positioned-
  element memory cost.

Both require rewriting `matvec()` (per-shard glyph columns instead of fallback runs + packs), `attention()`
(per-head columns instead of one query element + 12 nested banks), the LN stages (cross-chain statistics) and
the `reused_core` assembly (columns instead of nesting) — i.e. a new emitter, not a readback swap. **Step 4 of
the brief (integrate all 12 layers this round) is therefore not attempted**; §3 (Prototype B) is the deliverable
that de-risks the mechanism at full MLP scale with the real fonts, and §5 gives the residual risks and the order
of work for the rewrite.

## 5. Residual risks and the order of work for the rewrite

1. **Memory per positioned container** (§2b): ≈ 35 KB each, `visibility:hidden` does not help
   (`s-G12-…-hidden`: 2.2–2.5 GB, busy 2.35–2.46 s — identical). Before any 12-layer unroll, find the cheap form
   (candidates: `display:contents` wrappers are not possible for containers; try `contain:layout` on the chain
   root, dropping `container-type` from alternate levels, or 4 values per container via width/height packing
   E1 #14 style at 12 bits each). Variant A (reused graph) adds only one layer's worth (≈ +1 GB).
2. **Cross-shard sums inside `width: calc(Σ anchor-size())`**: exercised by Prototype B (12 terms per
   dimension); precision of the summed LayoutUnits is 1/64 px per term.
3. **Acceptable-anchor rule**: keep every chain container `position:fixed` and never let a `position:absolute`/
   `relative`/transformed ancestor sit between a chain and the viewport (any of those becomes the containing
   block and hides the anchors → silent zeros, the E5 #301 failure). Add a build-time check.
4. **Cycle rule**: an anchor that is a descendant of the anchored container resolves to the fallback. In
   variant A the loop bank stays a timeline hop precisely because the reused graph's outputs are descendants
   of its inputs.
5. **Layer-norm statistics across chains** (768 values ≠ one chain): 2 extra anchor levels per chain carrying
   Σx and Σx² (offset for sign, scaled ≤ 2^24 px) — untested.
6. The KV bank / attention restructuring per head is the largest emitter change and interacts with F5's bank
   work; do it after F2/F5 land.

### 3b. Results (V3; `results/proto-b-3.txt`, 3 trials each, fresh input per trial, battery)

**Ordering rule (`order-probe`, 3/3 identical):** a `position:fixed` reader nested inside an anchored OOF subtree
resolves (a) anchors in its own subtree/chain, (b) anchors in *in-flow* content anywhere (Prototype A `late`),
and (c) anchors inside other OOF roots only if that root comes **earlier in tree order** — regardless of nesting
depth on either side (`A6_C6`, `A6_C1` ok; `A1_B1`…`A6_B6` all 0; top-level readers placed *before* the chains
see nothing, placed *after* see everything). Emit columns in data-flow order and this is automatically satisfied;
violate it and the value is silently 0 (the E5 #301 symptom again). V2's shallow "range relay" placed before
the chains failed for exactly this reason; V3 computes the per-shard proj range locally under each fc chain and
lets the (later) out chains read the 12 range anchors as numbers first, then sum `anchor-size(--pⱼ_i) × --rⱼ`.

| variant | UpdateLayoutTree | Layout | Commit (frames) | busy ms | active ms | RMSE vs witness | max abs err | within 5e-3 |
|---|---|---|---:|---:|---:|---:|---:|---:|
| **b-chain V3** | **1** (3,089 el; 14–20 ms; 1,938 interleaved recalcs) | **1** (393–411 ms) | **1** | **512–535** | 463–484 | **3.6–4.0e-3** | 0.031–0.041 | 747–752 / 768 |
| b-timeline (emitter `matvec()`) | 3 (6,158 / 3,083 / 3 el; 212–221 ms) | 2 (154–160 ms) | 3 | 612–648 | 611–645 | 1.1–1.25e-2 | 0.14–0.18 | 479–508 / 768 |

The chain variant is **3× fewer frames (3 → 1; per boundary 1 → 0), one pass, 17 % less main-thread time, and 3×
lower error than the current transport on the same fonts, same inputs, same decode** (the timeline's extra error
is its ~14-bit float progress, E1 #2; both inherit the font path's 1/64-px snapping, so neither is bit-exact against
NumPy — the emitter's own witness RMSE is 0.034 vs float weights). Per-container cost inside the real page ≈ 200 µs
(393 ms / 1,938: the proj-chain containers evaluate 12-term `anchor-size()` sums and the interleaved recalcs
carry 256-axis `font-variation-settings` under 12 chain bottoms), i.e. 4–5× the synthetic §2b rate; a
layer's 4,400 containers would cost ≈ 0.9 s of layout on battery, still far below the ≈ 1.3 s/layer of frame +
animation overhead being removed.

## 6. Summary (what landed, what did not, what to do next)

* **Delivered**: the transport map (§1); a validated frameless gather primitive (§2: 256–500 values per chain in
  one UpdateLayoutTree + one Layout + one frame, exact to the pixel, ≈ 50 µs per container synthetic, ≈ 200 µs in
  the real MLP); its scaling to a token's worth of gathers in one lifecycle (§2b: 50k containers, 1.6–1.9 s
  layout, exact); a real layer-0 MLP 768→3,072→768 on the repo's HVAR shards that beats the emitter's own
  timeline transport on frames (3→1), passes (5→2), main-thread time (−17 %) and error (3× lower) (§3b); and the
  four Chromium rules the design must obey — containing-block acceptability (use `position:fixed` only),
  OOF-root tree-order visibility, the 512-element parser nesting cap (≤ ≈ 500 values per chain; shadow roots do
  not help because anchor names are tree-scoped), and the ≤ 2^24 px precision window (§2, §3b).
* **Not delivered**: step 4 (emitter integration for 12 layers). §4 shows it is a re-architecture of `matvec()`,
  `attention()`, the LN stages and the `reused_core` nesting into per-shard/per-head fixed columns (≈ 4,400
  containers + 27k anchors per layer), not a readback swap; with the remaining round budget and the shared Chrome
  lock it could not be built and verified. No `bundles/F3` was produced; nothing under `tools/` or
  `experiments/` was modified (the tools copy under `F3/tools` is unmodified; `diff -rq` shows no changes).
* **Recommended order for the rewrite** (variant A of §4, keeps the reused graph and the loop-bank latch):
  1. fc→proj (the largest boundary, already prototyped here: reuse `gen_proto_b.py` `chain_page()` as the
     emitter template); 2. attn-proj→r and proj→out with the `r` residual re-published as in-flow anchors;
  3. per-head attention columns (interacts with F5's bank work — do after F5); 4. QKV per-head chains;
  5. then Fix 6 (`@container style()` stamps replace the SMIL receipts) — with 1 latch hop per layer the
  handshake shrinks to the loop bank alone. Expected: frames/token 85 → ≈ 15, ScrollTimeline invalidations
  110k → ≈ 1.5k, −8 to −12 s/token; memory +≈ 1 GB unless the per-positioned-element cost (§5 #1) is reduced.
