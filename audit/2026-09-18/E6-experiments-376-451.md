## 2. Mechanism families

### 2a. SVG-filter LayerNorm reduction backends (376–388; plus variants 391–402)
Question: replace Skia's large-kernel `feConvolveMatrix` reductions (three 256-tap per LN) with blur/tiling/hierarchies.
Best measured: hier4 exact locally and 13.4% faster isolated (828 vs 940 ms); tiled Gaussian σ384×3 is the most accurate cheap option (0.06123 vs 0.08234 RMSE) with 3–6% latency gain; r192 is the most accurate overall (0.04525) at +5%.
Blocker: none of them help the connected two-block chain (hier4 everywhere raises post-LN RMSE 0.0608→0.1110 with zero latency change; Gaussian gives 6.4% but doubled frames). Two- and one-shard reductions (384/768-tap) are numerically invalid in Chromium. The doc's own conclusion: "neither is a general full-GPT replacement."

### 2b. Live multi-block SVG chain (389–402, 435–437)
Question: connect block 0 → block 1 fully live in SVG filters with no JS.
Best measured: two complete blocks at 1,989 ms median (stable 1.90–2.05 s), post-next-LN RMSE 0.06078, 4.2 MB HTML. Direct mixed-context c_proj 1.86× and centered QKV ~2× were the two real wins.
Blockers: (i) raster/screenshot stage dominates and scales ~1 s/block ⇒ ~12 s for 12 blocks even before the output head; (ii) removing the intermediate raster boundary hangs Chromium (>3 min); (iii) 8-bit accuracy: the offline W8A8 screen (438) already fails at 58% next-token agreement, so the doc halted extension past two blocks. gpu-veto variant has no result.

### 2c. SVG attention layout sweeps (404–424)
Question: which QKV/attention surface geometry is fastest in Chromium?
Best measured: 64-wide head-local surfaces, 256-row shards, centered single-convolution QKV (416): 300.6 ms QKV / 465.4 ms through attention / 563–584 ms through residual; context RMSE 0.00526.
Blockers: every wider geometry loses — token batching 1.35× slower, head groups 0.51–0.74×, 768/2,304-wide contiguous 35–39% slower, spatial head-lane batching 0.989× (size-only win 10×). Shard 384 is fast but invalid (RMSE 0.83). Merging live surfaces via feOffset/feMerge or feTile renders zero; every valid path needs an explicit second `<filter>` (raster boundary). Doc's summary: "convolution and raster work — not repeated markup — dominate."

### 2d. SVG 8-bit precision escapes (403, 426, 427, 431–434)
Question: get more than 8 bits through a computed SVG surface (extra channels, bit planes, dither, hi/lo bytes, packed kernels).
Best measured: nothing beats the ordinary range-scaled signed product (0.01738 RMSE on a c_proj slice; 0.00417 on the bitplane fixture). Extra channels are 66,000× better *before* the first computation and identical to 1 channel after it.
Blocker (the doc's own words): "Chromium quantizes each SVG-filter primitive before a computed scalar can be split into high and low channels"; "a true general fix would require Chromium to expose an F16 SVG-filter backing format." packed-kernel-matrix and product-dither have no saved numbers.

### 2e. Offline W8A8 numerical screens (425, 428, 430, 432, 438, 439) — Python only
Question: can smarter quantization/calibration/ensembling/rotation make the 8-bit SVG representation faithful?
Best measured: three-phase RGB dither 492/512 (upper bound, not implementable with current R/G ± lanes); rank-128 head map 488/512; two-fold fixed calibration 53/64; ensemble 52/64; rotation never improves winners.
Blocker: full 12-block causal generation retains 28/48 teacher-forced tokens and diverges after 2 tokens; "the complete numerical screen fails before browser overhead is considered." All of these are numerical models — none of the corrections were validated in Chromium.

### 2f. Timing model (440)
Best/only result: transport-free floor 775.7 ms/block at context 16 (1.31× max from transport removal); 12 blocks ≥ 9.3 s; 13× target needs ~78 ms/block. Blocker: stage-local HVAR shaping + layout work itself is ~10× too slow; "a transport primitive by itself only removes the first problem."

### 2g. Font-backend selectors (441, 442)
Both blocked by Chrome: TrueType bytecode interpreter is inactive on Chrome/macOS (FreeType `E`); TTC `#face` fragments always resolve face 0 (also true for WPT's ahem.ttc). Best result: a 143,628-byte collection would hold 64 shared-HVAR faces if the selector worked.

### 2h. View-timeline / typographic geometry→number transport (443–451)
Best measured: named view timelines recover widths exactly (37/41) and HVAR outputs to ~0.1 (−109.612 vs −109.75), inherit into children, and 3,072 parallel readbacks cost 260 ms / 750 KB (fixed widths). Four values per subject work exactly (23/37/29/41) but at scale give only 4.8% over two-value.
Blockers: typographic `display:contents` merge yields 0 width; timeline/animation/registered-property count, not subject count, dominates cost ("animation/property count still dominates"); packed two-value carriers lose low bits at 16.7M-px coordinates. These probes are the origin of the later view-timeline-fc/mlp/two-block line (outside this slice), which reached 966 ms for one FC stage and 3.92 s for two blocks.

## 4. Surprising / positive results not followed up

1. **r192 LayerNorm shards** (385): 0.04525 RMSE vs 0.08234 baseline (45% lower error) for ~5% latency. Never adopted in any connected chain even though accuracy, not speed, is what killed the SVG branch (438).
2. **Tiled-Gaussian LN** (376): better accuracy *and* 3–6% faster, but shelved because of two doubled frames in one paired run; no retry with the later alternating-URL invalidation methodology that the same doc says removes doubled samples.
3. **hier4 LN isolated 13.4% speedup with bit-identical output** (382): rejected on a connected test where *all three* LNs were replaced at once; the doc reports block-1 LN1 alone still gave 5.1%. No partial-replacement follow-up.
4. **Repeated-sum convolution broadcast** (406): 126.1 vs 138.3 ms (~9% faster than feTile) and it survives live-result boundaries where feTile renders zero. Only used inside the contiguous path that lost for other reasons; never applied to the retained head-local path.
5. **Spatial head batching 10.2× bundle reduction at equal latency** (405): explicitly parked as "bundle-size technique only"; the 12-block page-size problem (7.9 MB HTML + 49 MB PNG in svg-filter-matvec) was never revisited with it.
6. **Three-phase RGB dither +1.95 pt held-out top-1** (432) and **rank-128 head map +1.17 pt at zero runtime cost** (425): both left as "optional refinements"; neither was tried in Chromium. Combined, they are the only accuracy levers measured that did not cost latency.
7. **spread-8 rotation** (430): RMSE 0.1235 / max 3.70 vs baseline 0.1581 / 6.31 on 16 cases — the largest max-error reduction of any offline screen — but 14/16 winners, so dropped without a larger-N or calibrated run (the cal32/eval32 run used spread-4 only).
8. **GPU-veto** (401) and **packed 2D kernel** (426) were built but never reported; both are cheap to measure with existing harnesses.
9. **TTC metric bank** (442): a 143 KB file holding 64 shared-HVAR faces is the most compact matrix-row representation in the slice; blocked purely by Chrome's missing `#face` fragment support (tracked in caniuse issue 6566) — worth a periodic re-check rather than a re-design.

## 5. Skeptic's notes

- All latency numbers in this slice are Playwright screenshot/navigation timings in headless Chrome on one macOS machine; several docs warn that twelve-capture validations (8.8–19.8 s) are "not single-inference latency or token rates."
- The two-block SVG chain (398) is the only entry that measures more than one block; "~12 s for 12 blocks" is my extrapolation, not a measured number.
- 425/428/430/432/438/439 are NumPy models of the SVG backend; the docs themselves say they are "optimistic about runtime overhead" and that aggregate RMSE "did not reliably predict" browser token failures.
- transport-free-timing-model (440) is arithmetic over saved JSON; its 202.9 ms attention-internal figure is a subtraction, not a timed stage.
- view-timeline-scale-* (448–450) use fixed-width subjects, not HVAR glyphs; the docs say 260 ms "is not yet a matrix-stage benchmark."
