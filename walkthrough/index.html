GPT-2, through the browser
An illustrated walkthrough

One token · twelve layers · ordinary browser machinery

From a word

GPT-2 predicts the next piece of text. This project makes a browser do the prediction using the machinery it normally uses to style a page and measure letters.

This walkthrough follows the full GPT-2 demo selected by the launcher: one input token, 12 layers, up to eight new tokens. The diagrams use small teaching examples. Their controls use JavaScript; the model page itself does not.

01 / THE WHOLE SYSTEM

The browser is the calculator.

A model is a collection of numbers learned from examples of text. These numbers, called weights, determine how the input is transformed. They stay fixed while the model predicts.

There are two separate jobs: prepare the model once, then run its calculations for each new token.

Before calculating, the page checks known letter widths in all 261 model font faces. A missing font would give the wrong numbers, so the calculation waits until those checks pass.

02 / THE INPUT

A token is a piece of text
with a number attached.

The model does not read letters directly. It uses a fixed list of 50,257 text pieces. A piece may be a word, part of a word, punctuation, or a space with letters after it. Each piece has an ID: its number in that list.

The current full-model demo starts with a menu of single-token prompts. Selecting “Hello” supplies ID 15496.

What about typing a whole sentence?

This full-model demo does not accept a free-text prompt. An earlier TinyStories experiment does: an editable style rule supplies text to generated fonts. The fonts repeatedly combine letter pieces according to GPT-2’s saved merge rules. This splitting process is called tokenization.

Those fonts expose the resulting token IDs as letter widths. CSS reads them and feeds the model. That separate page accepts up to four prompt tokens; it is not the input path of the full GPT-2 demo explained here.

03 / GIVE THE TOKEN A WORKING REPRESENTATION

Look up 768 numbers.
Add where the token sits.

An ID only identifies a piece. To calculate with it, the model looks up a row of 768 learned numbers. This row is called an embedding. Think of it as the token’s starting pattern, not a dictionary definition.

Another learned row describes the token’s position: first, second, and so on. Add the two rows, number by number. The result is the working row that enters layer 1.

In this browser: a special font contains the token lookup table. Two font controls select a group and an entry within it. The widths of 768 special characters encode the 768 numbers. CSS then adds the saved position row.

How does ID 15496 select the row?

Divide it into a group of 256 and an offset: 15496 = 60 × 256 + 136. The font controls named GRUP and LOCL receive 60 and 136. The font returns that entry’s widths. The two controls select data; they do not infer the meaning of “Hello.”

04 / THE REPEATED CALCULATION

Multiply pairs. Add them up.
Let a font do it.

Much of GPT-2 is the same operation: take the working numbers, multiply each by a learned weight, and add the products. Add one more learned number, called a bias. That gives one output number. Different sets of weights produce the other outputs.

A variable font normally has controls for things like thickness and width. This project creates fonts with hundreds of controls. Each input number sets one control. The font’s internal width rules contain the weights.

A positive starting width allows negative answers to be represented. Long input rows are split across font pieces; laying pieces next to one another adds their widths. CSS removes the starting widths and restores the numerical scale.

What is rounded, and why does scale matter?

The main layer weights are stored as 9-bit row codes; each row also has a scale that converts its codes back into approximate weights. “9-bit” means a compact code with roughly 512 possible values. The final scoring weights use 16-bit codes.

The live input row is divided by a value slightly larger than its largest absolute number. That keeps the font controls within their supported range. After measuring, CSS multiplies by the input scale and weight scale. These scales come from the current input and model weights, not prepared answers.

The font table that changes character widths is called HVAR. You may see that name throughout the source.

05 / PASS THE ANSWER ALONG

A width must become
a number again.

After the font calculation, the answer exists as a length on the page. The next calculation needs a number. The project uses the browser’s layout and animation machinery to cross that gap.

An invisible element sits in a fixed scroll area. A view timeline reports a progress value based on the element’s size and position. Changing the element’s width changes that progress—even though nobody scrolls. An animation copies the progress into a CSS number.

CSS then removes the encoding offset and scale. The recovered number can set the next font’s controls. This repeats throughout the model.

Other connections read a named element’s size directly with anchor-size(), or read a containing box’s size through container units. These are ways to move calculated values through layout.

These elements are mostly invisible. The calculation happens when the browser resolves styles, measures characters, and lays out boxes. Painting the visible text is a later step.

06 / THE MODEL’S ARCHITECTURE

One layer, taken apart.

GPT-2-small has 12 layers. Each takes 768 working numbers and returns 768 updated numbers. Each layer first mixes information from available tokens, then transforms the current token’s row.

Follow the steps below. The two side paths show rows being kept and added back: the layer’s input at step 4, then the updated row at step 8.

The exact sequence, in compact form

Let x be the incoming row. Let r be the row after attention:

r = x + mix(attention(rescale(x)))
output = r + shrink(bend(expand(rescale(r))))

Each “mix,” “expand,” and “shrink” is a learned weighted sum plus bias. The mean is the row’s average. Variance is the average squared distance from that average. Rescaling subtracts the mean and divides by √(variance + 0.00001), then applies a learned scale and offset. The extra 0.00001 prevents division by zero.

All 12 layers use this same sequence, with different learned weights. A final rescaling after layer 12 prepares the row for vocabulary scoring.

07 / ATTENTION: READ THE AVAILABLE CONTEXT

Decide what to take
from each token.

From the rescaled row, three learned transformations produce three rows of 768 numbers. Their names describe their jobs:

Query

What the current token uses to compare itself with the available tokens.

Key

What each token offers for that comparison.

Value

The information taken from a token if it gets attention.

Each row is divided into 12 groups of 64. These are the 12 attention “heads.” Each group makes its own comparisons and its own mixture. This lets the model make several different mixtures at once.

123456789101112

12 heads × 64 numbers = 768 numbers.

Convert scores into positive shares that add to 1. Then multiply every value row by its share and add the rows. A higher share contributes more of that token’s numbers. The result is 64 numbers per head. Join the 12 results to get 768 again.

In this version: special fonts multiply query and key numbers, and multiply value numbers by their shares. CSS calculates the shares; adjacent letter widths add the weighted values. Layout returns the mixture to the main calculation.

For the first input, “Hello,” there is only one available token. Every head gives it 100% of its attention. Looking back across several tokens begins on the next prediction.

Exactly how scores become shares

Subtract the largest score from every score. Apply exp() to each result, then divide each result by their total. This is called softmax. Subtracting the maximum keeps the arithmetic manageable without changing the shares.

The score divisor is 8 because each head has 64 numbers and √64 = 8. This prevents the sums from growing too sharply as the number of terms increases.

08 / UPDATE THE CURRENT TOKEN

Mix the context.
Then transform the row.

A learned weighted sum mixes the 12 heads’ combined result. Add that to the layer’s original input. This addition is a residual connection: the layer learns a change to the row, while retaining the row itself.

Rescale the result. Expand 768 numbers into 3,072, bend each number with a smooth rule, and use another learned weighted sum to return to 768. Add this change to the row saved before the expansion.

In the browser: fonts do the expansion and shrinking. CSS evaluates the smooth bend and both additions. This part does not separately read earlier tokens; it transforms the current row, which already contains information from attention.

09 / REPEAT THROUGH ALL TWELVE LAYERS

Twelve sets of weights.
One reusable page structure.

The updated row enters the next layer. Repeat the same sequence with that layer’s weights. After layer 12, the row is ready to predict.

The current demo reuses one set of calculating elements for all 12 layers. CSS switches the weights and uses alternating storage banks to pass the completed row back as the next layer’s input.

What survives when a new token starts?

Each layer saves the keys and values it produced for each token. On the next token, attention uses those saved rows instead of recomputing the older tokens. This saved memory is called the key/value cache.

This version keeps each head’s 64 numbers together as a font-control list, plus a scale. A long-delayed CSS transition holds the old value. Only the current layer’s current token slot is allowed to update.

How can a transition act like memory?

Normally a transition holds a previous value briefly before changing it. Here, the delay is 86,400 seconds—one day—with a one-step change at the end. During the bounded run, a held value therefore stays put.

For a writable slot, the rule removes the transition so the new value takes effect. When that slot becomes an older slot, the delayed transition retains its last value. For a list of font controls, the browser holds the whole list as one discrete value.

The two banks that hand rows between layers are temporary storage. The per-layer key/value banks are separate storage for earlier tokens.

10 / THE OUTPUT

Score every possible token.
Choose the highest.

After layer 12, rescale the final row once more. Compare its 768 numbers with each vocabulary token’s learned row: multiply matching numbers, then add them. This produces 50,257 scores.

The scoring rows come from the same learned embedding table used at the input, stored here in the output font’s rounded representation. A larger score makes a token a stronger next-token candidate.

In the browser: fonts turn scores into widths. The candidates in each group occupy the same CSS grid cell, so the group’s width follows its widest candidate. Small trees of size comparisons find the winning group.

A second pass scores the selected group’s entries again and gives matching entries small widths that encode their IDs. This separates large score widths from small identity widths, avoiding lost digits in a single oversized width. Fixed tie rules choose one ID if scores match.

The model always chooses the highest represented score. This is called greedy decoding. It does not roll a random choice, and it does not need to convert the output scores into percentages.

Why 197 groups?

196 × 256 = 50,176. The remaining 81 entries make group 197. Once a winning group and its local entry are known, token ID = group index × 256 + local index, counting both indices from zero.

The final scores are rounded into width buckets. The winner is exact for the runtime’s represented scores; it is not guaranteed to be the winner of unrounded GPT-2 on every input.

11 / COMPLETE ONE PREDICTION

Show the piece.
Feed its ID back in.

For the saved “Hello” run, the first winner is token 11: a comma. A CSS counter style maps that number back to its text piece. Generated content displays it, so the page now reads “Hello,”.

The winner’s ID is stored and carried back to the embedding lookup. The position advances by one. The same 12-layer process runs again, now with the previous token’s keys and values available.

A completion marker travels with each result. The next stage accepts it only if it matches the current calculation. This prevents an old width or an earlier winner from advancing a new calculation before it is ready.

The 1 ms handoff animations are signals, not a promise to finish the model in 1 ms. The browser still has to complete the font, style, and layout work.

Each new token starts a fresh prediction. The page has eight output slots and a finite set of control signals prepared in advance. It stops after eight outputs or the end-of-text token, ID 50256. Pause takes effect at a token boundary; Reset reloads the page and clears the held state.

Text piece → ID → 768 numbers → 12 layers → 50,257 scores → one ID → next text piece.

SOURCES & LIMITS

What this page describes.

This is the reusable, font-vector version at demo-font-vector-twelve, selected by the launcher. Earlier pages and separate optimization experiments use different ways of carrying and storing numbers.

Its saved full run produced “Hello, I’m sorry, but I’m” in about 403 seconds, including loading. All eight output IDs matched both tested numerical references. That is evidence for this run, not proof that rounded weights and browser arithmetic always reproduce the original model.

The run used roughly 3.8 GiB of peak sampled renderer memory. Much of the cost comes from resolving and carrying large amounts of style state, not displaying the sentence. Reusing the calculating elements reduces duplication, but the model still performs all 12 layers and scores the full vocabulary.
