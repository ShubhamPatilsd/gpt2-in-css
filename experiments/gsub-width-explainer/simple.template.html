A plain explanation of the browser experiment

Why the working font circuit is still too narrow

We got the browser to carry two small numbers through sixteen calculations inside a font. GPT-2 needs hundreds of numbers to affect one another. That is the gap.

“Width is the remaining obstacle” means we know how to make a long chain with a tiny amount of information. We do not yet know how to make that chain handle GPT-2’s large, connected groups of numbers at a useful speed.

1 · First, what does “width” mean?

It means how many numbers can take part in one connected calculation.

A single number is just a value such as 3 or −0.42. A list of numbers is often called a vector. One item in that list is a coordinate.

The experiment
[3, 5]

Two coordinates. Each is a whole number from 0 to 15.

One GPT-2 token state
[x₀ … x₇₆₇]

768 coordinates. They can be positive, negative, and fractional.

The model does not give each coordinate one simple meaning such as “grammar” or “emotion.” Meaning is spread across many coordinates.

There are two ideas that are easy to mix up:

How many numbers exist: GPT-2 keeps 768 numbers for the current token.

How many numbers meet: in an important GPT-2 step, one new number is made from all 768 old numbers. This second part is the real problem.

“Width” here does not mean the width of the browser window. The experiment does use a measured text width to return its final answer, but that is only the output channel.

2 · What is the browser doing?

It turns numbers into text measurements, then measurements back into numbers.

The existing GPT-2 page

The model already uses custom fonts to do large number operations. Current values are sent into a variable font. The font stores model weights and turns weighted values into horizontal text lengths. The page then reads those lengths back as numbers for the next step.

CSS numbers → font settings → text length → CSS numbers

This works, but crossing back into the page can make the browser update styles and layout. The browser spends a lot of time moving results from one stage to the next.

The newer font experiment

The newer experiment keeps intermediate answers inside the font. A number is represented by the identity of an internal font symbol, called a glyph. Font rules replace one set of glyphs with the next set. Only the final answer becomes a text length.

Two input numbers → internal font symbols → more internal symbols → one final text length

This does not make the work disappear. The font system still follows rules. The hope is simply that following several rules internally can cost less than repeatedly publishing intermediate numbers back to the page.

3 · The small circuit that works

Two numbers enter. Two numbers leave. Repeat sixteen times.

Here, “circuit” means a connected chain of operations. It is not a physical electronic chip. The output from one font rule becomes the input to the next font rule.

The two numbers are named x and y. Each can be 0 through 15. That gives 16 × 16 = 256 possible pairs.

new x = y
new y = (x + y² + 3y + step number) modulo 16

“Modulo 16” means: after doing the arithmetic, keep the remainder after division by 16. That keeps every answer between 0 and 15. This rule was chosen to create a small, nontrivial, reversible test. It is not part of GPT-2.

What happens inside one step?

Suppose the current pair is [3, 5]. The font first joins those two state glyphs into one glyph that stands for the whole pair. The pair gets number 16 × 3 + 5 = 53. The next rule turns that joined glyph into the next pair, [5, 12].

The font contains one rule for each of the 256 possible pairs at each step. Python calculated those rules when the font was built. The browser selects the matching rule; it is not independently solving the formula.

How does the final pair become a page number?

The font packs the final pair into one value, 16x + y, then adds 64. It gives the final invisible glyph that many units of horizontal width. The page measures that width, subtracts 64, and separates x from y again.

measured width = 64 + 16x + y

Breaking step 8 leaves the symbols in the wrong form. The later rules no longer match, so no final-width glyph appears. That is evidence that the steps are truly connected.

4 · What did the successful result prove?

It proved that a narrow chain can become worthwhile when it is long enough.

The test compared the font chain with the same sixteen-step rule written directly in CSS. Both paths included receiving inputs and producing a usable final number.

For a batch of 256 separate circuits, the sixteen-step font path took 7.0 milliseconds with fresh text. The direct CSS path took 10.2 milliseconds. The font path was about 31% faster in that particular test.

At one, two, and four steps, direct CSS was faster. At eight steps there was no clear advantage. The win only appeared at sixteen steps. That is why the result is about depth: the input and output costs were spread over more internal work.

The font remained narrow throughout. It always carried just two four-bit numbers.

Many separate copies still do not interact

256 separate circuits, each carrying two numbers. No copy sends a number to another copy.

This distinction matters. The timing test used 256 separate two-number circuits so the measurement would be large enough to see. It did not create one circuit containing 512 connected numbers.

5 · Why GPT-2 is harder

One new number can depend on all 768 old numbers.

Inside each GPT-2 block is a step usually called the MLP. First it turns 768 input numbers into 3,072 new numbers. Each one of those 3,072 outputs is a weighted sum of all 768 inputs.

one output = bias + input₀ × weight₀ + input₁ × weight₁ + … + input₇₆₇ × weight₇₆₇

A weight says how strongly one input contributes, and whether it adds or subtracts. A bias is one extra fixed value added at the end.

This is not 384 separate two-number problems. All 768 contributions must eventually meet in the same running total. Also, each input is reused for many different outputs.

6 · Why not make one enormous font table?

The number of possible inputs grows far too quickly.

For two numbers that each have 16 possible values, there are 16 × 16 = 256 pairs. Add a third number and there are 4,096 groups. Add a fourth and there are 65,536.

possible groups = (values per number)number of numbers

Try the count

256

This counts input combinations. It does not predict file size or speed. Selecting 768 with four bits is a thought experiment; GPT-2 does not use the toy’s four-bit values.

A normal OpenType font can name at most 65,535 glyphs. The toy uses a different joined glyph for each possible pair. Applying that exact method to only four four-bit numbers would already need 65,536 joined glyphs, before counting any other glyphs.

For 768 four-bit numbers, a full table would need one row for each of roughly 5.8 × 10924 possible groups. That is not remotely practical.

This rules out the brute-force table. It does not prove that fonts cannot handle more than two inputs. It tells us we need to build the answer from smaller reusable operations.

7 · A possible way forward

Add small pieces and carry a running total.

Ordinary arithmetic does not memorize the answer for every possible group of inputs. It multiplies each input by its weight, then adds the products into a running total.

2×3 + 3×(−2) + 1×5 + 4×1 + bias 1 = 10

The project already contains one encouraging building block: another font added every possible pair of eight-bit numbers exactly. It did not list all 65,536 byte pairs in one large table. It split each number into smaller four-bit pieces, added those pieces, and carried overflow to the next piece.

That shows that small font rules can be joined to do larger arithmetic. But it was not faster than CSS after the full input and output path was counted. It also did not implement signed multiplication, a 768-term running total, or GPT-2’s fractional values.

The next useful experiment

Start with four connected inputs. Give them positive and negative weights. Make every input affect one shared output. Keep the result inside the font and use it in one more operation before returning it to CSS.

Then try eight inputs and sixteen. At each size, measure whether every answer is correct, how much rounding occurs, how many font rules are needed, how much time shaping takes, and whether the whole path is faster than a fair CSS version.

If that scales sensibly, the next test can use real checkpoint weights and real model inputs. Only after that works would it make sense to integrate a whole model stage and measure token time.

The core question is simple: can enough small pieces communicate inside one font run that the saved page-update work is greater than the added font work?

8 · What we know

The narrow result is real. The wide result is still a proposal.

  • Proved in the browser: the two-number font circuit gives the exact result for all 256 starting pairs, through sixteen connected steps.
  • Measured: at sixteen steps it beat the fair direct-CSS comparison for this small batch. Shallower versions did not show the same win.
  • Known from the model: GPT-2 has 768-number token states, and one MLP output combines all 768 inputs.
  • Ruled out: one lookup row for every possible 768-number input group.
  • Not yet proved: a practical connected font circuit for a wide weighted sum, acceptable model accuracy, or any end-to-end token speedup.
